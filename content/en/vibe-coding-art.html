In early 2025 Andrej Karpathy gave a name to a way of working many had started to practise: vibe coding. You describe what you want in plain language, an AI writes the code, you run it, you look, you ask for changes, and you stop reading the code at all. For a production server, that is a risk. For an artist, it is a door: the distance between an idea and a moving image has never been so short.

What you get. A map of the creative uses of vibe coding (visuals, shaders, music, motion, interaction), how to practise them with your own local models and no subscription, and the simple rule we follow so that sketches stay fun and nothing fragile ends up in production.

1. What changes for creators

Creative coding has existed for decades: writing programs whose output is a picture, a sound, a movement. It always had a barrier: you had to learn the language before making anything. Vibe coding lowers that barrier. The skill moves from syntax to intention and judgement: describing a mood precisely, recognising what works, asking for the right change.

2. The offshoots in digital art

  • Generative visuals: sketches in p5.js or Processing, described rather than typed: "particles that drift like ash, rising slowly, colours from ember to grey". Change the seed, get a series.
  • Shaders: small GPU programs that compute every pixel, the art of Shadertoy. Notoriously hard to write by hand, surprisingly approachable by description and iteration.
  • Live-coded music: environments such as Strudel, TidalCycles or Sonic Pi, where a pattern of text is a rhythm. A model proposes a pattern, you edit it live, on stage if you like: the algorave scene has done this for years.
  • Live visuals: Hydra-style video synthesis in the browser, patched by code and played like an instrument.
  • Motion design as code: a video written as an HTML composition, timed and animated, then rendered. Our explainer clips use this approach (see creative skills).
  • Interactive pieces and mascots: our FoxBot's animation engine, its sprite sheets and its moods were built with agents, by describing behaviour rather than drawing frames (see the homelab cat for the same idea).
  • Images, video and music generators: not code, but the same posture: describe, look, refine (see the studio).

3. Practise it locally

  1. Open a coding agent on your own model (OpenFox) in an empty folder.
  2. Ask for one HTML file with p5.js and a single sketch; open it in the browser.
  3. Describe what you see and what you want instead, in feelings and constraints, not code: "slower", "more breathing space", "colours of a winter morning".
  4. Keep the seeds and the versions you like: a sketch is a series, not a single image.

A small local model is enough for sketches of a few dozen lines. Long, structured programs are where it struggles; that is also where vibe coding stops being the right tool.

4. Where we draw the line

Vibe coding is perfect when the cost of a mistake is an ugly frame. It is dangerous when the code runs unattended, holds data or faces the internet: a model writes plausible code that may never have run, and "it looks fine" is not a test. Our rule, from the deterministic doctrine: vibe for sketches and art; read, test and measure for anything that runs on its own.

Traps

Rights still matter. Generating "in the style of" a living artist, or from their work, raises questions the tool does not answer for you. Build your own style; credit what inspires you.

A vibe-coded web page published as is may carry a key, a debug route or an open form. Before publishing, read it once (see the audit).
