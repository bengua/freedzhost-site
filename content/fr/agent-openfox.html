La plupart des agents de code sont construits pour un modèle de pointe dans le cloud et tolèrent tout juste un modèle local. OpenFox fait l'inverse : un assistant libre (MIT) pensé d'abord pour des modèles servis sur votre machine. C'est l'agent qu'on ouvre pour le travail de tous les jours, sans coût au jeton.

{{diagram:agents}}

1. Où il se place

OpenFox parle à un point d'accès compatible OpenAI. Ne le pointez pas sur un serveur de modèle : pointez-le sur votre passerelle de modèles. La passerelle sait quel modèle est chargé sur quelle carte ; OpenFox ne connaît qu'une adresse stable et un nom de modèle.

npm install -g openfox      # Node 20 ou plus récent
openfox                     # premier lancement : choisir le fournisseur, saisir l'adresse de la passerelle

Faites-le tourner sur la machine qui porte les cartes, et atteignez-le d'ailleurs (portable, téléphone) par votre réseau privé. L'agent lit et écrit alors les fichiers là où se trouve le travail, pas à travers un partage réseau.

2. Suivre le modèle réellement chargé

Sur un seul serveur maison, le modèle change : un gros pour le code le soir, un petit pendant qu'un jeu ou une génération d'images occupe la carte. Si OpenFox réclame un modèle qui n'est plus chargé, chaque requête échoue. Nous faisons tourner un petit suiveur qui lit le modèle déclaré par chaque carte et réécrit le modèle par défaut d'OpenFox en conséquence. La règle : la configuration de l'agent suit le matériel, jamais l'inverse.

3. Garder la liste d'outils courte

Chaque outil qu'un agent peut appeler est décrit dans chaque requête. Notre premier tour pesait 8 455 jetons avant que l'utilisateur ait tapé un mot, surtout des descriptions d'outils. Avec une fenêtre de 32k sur un petit modèle, c'est un quart de perdu. Ce qui a marché :

  • un seul serveur d'outils (MCP) permanent au lieu de cinq ;
  • des outils chargés à la demande, quand la tâche en a besoin ;
  • un prompt système court : l'attention du modèle est la ressource rare.

4. Le tester là où il sert

Un modèle qui répond à un curl n'est pas un agent qui marche. La seule preuve, c'est une session dans OpenFox où le modèle appelle un outil (lit un fichier, lance un test) et se sert du résultat. Nous avons compté plusieurs « ça marche » qui ont échoué au premier vrai appel d'outil : le modèle répondait du texte mais ne produisait jamais d'appel d'outil valide au format de l'agent.

Pièges

Ne laissez jamais deux processus écrire le fichier de configuration de l'agent en même temps. Deux enregistrements de serveurs d'outils en parallèle nous ont laissé un config.json corrompu et un agent qui ne démarrait plus. Enregistrez les outils un par un, et gardez une copie du fichier avant de le modifier.

Un petit modèle qui boucle sur la même commande n'est pas têtu, il a perdu son contexte. Raccourcissez la tâche, pas la patience : un fichier, un changement, un test.
